# Part B Report: Reproducing and Fixing Tailwind Dynamic Classes

## Objective

Demonstrate why a Tailwind CSS class assembled through Jinja
interpolation can work in a browser-based development demo but be
missing from compiled CSS, then show two ways to ensure the required
styles are generated.

## Project setup

The demo uses:

-   **Flask** to render Jinja templates.
-   **Jinja** to insert the `color` variable into the component.
-   **Tailwind CSS v4 Browser script** on the development page.
-   **Tailwind CSS v4 CLI** to generate the production stylesheet.

Relevant files:

``` text
part-b/
├── app.py
├── input.css
├── static/
│   └── output.css
└── templates/
    ├── color-card.html
    ├── demo-dev.html
    └── demo-production.html
```

## 1. The original bug

The original component used this class:

``` html
<div class="rounded-lg p-6 text-white bg-{{ color }}-600">
  This card uses the {{ color }} colour.
</div>
```

The Flask route passed `color="purple"`. After Jinja rendered the
template, the browser received the class `bg-purple-600`.

### Development result

The development page loaded Tailwind's browser script. The script could
inspect the rendered DOM and generate the `bg-purple-600` style, so the
card appeared purple.

### Production result

The production page loaded the CSS generated by the Tailwind CLI. With
automatic source detection disabled and only the `part-b/templates`
folder scanned, Tailwind could not infer the complete class name from
the source text `bg-{{ color }}-600`. The compiled stylesheet did not
contain the `.bg-purple-600` utility, and the purple background
disappeared.

### Why it happens

Tailwind scans source files as text for complete class names. It does
not execute Jinja expressions or predict every possible value of a
variable. A class assembled from fragments can therefore be missed
during CSS generation.

This demonstration compares the browser-based development script with
the compiled CLI stylesheet. It does **not** mean the Tailwind CLI
automatically detects dynamic classes in development but removes them
only in production; the two demos use different ways to generate styles.

## 2. Fix 1 --- Use a static class map

Replace the interpolated class with complete class names in the
template:

``` html
{% set color_classes = {
    'purple': 'bg-purple-600',
    'blue': 'bg-blue-600'
} %}

<div class="rounded-lg p-6 text-white {{ color_classes[color] }}">
  This card uses the {{ color }} colour.
</div>
```

### Why it works

The complete strings `bg-purple-600` and `bg-blue-600` now appear in the
scanned template source. Tailwind can detect these classes and generate
their utilities. Jinja selects the appropriate class for the current
`color` value.

**Best for:** Applications with a known, limited set of possible
classes. It keeps the allowed class choices explicit in the template.

## 3. Fix 2 --- Explicitly include utilities with `@source inline()`

The Part B Tailwind input file can explicitly request the classes:

``` css
@import "tailwindcss" source(none);

@source "./templates";

@source inline("bg-purple-600 bg-blue-600");
```

### Why it works

-   `source(none)` disables automatic source detection.
-   `@source "./templates";` tells Tailwind which templates to scan.
-   `@source inline("bg-purple-600 bg-blue-600");` explicitly requests
    both utilities, so Tailwind generates them even if they are not
    found in the template text.

**Best for:** A known list of utilities that must always be present in
the generated stylesheet, including classes that cannot be discovered by
scanning source text.

## 4. Build and test commands

Run these commands from the repository root:

Build the Part B production stylesheet:

``` powershell
npx @tailwindcss/cli -i ./part-b/input.css -o ./part-b/static/output.css --minify
```

Check whether the compiled CSS contains the purple utility:

``` powershell
Select-String -Path .\part-b\static\output.css -Pattern "\.bg-purple-600\{"
```

-   No matching utility means the compiled stylesheet does not include
    that rule.
-   A match means the rule was generated.

The browser should be refreshed with **Ctrl + F5** after rebuilding to
avoid testing a cached stylesheet.

## Conclusion

Dynamic class fragments such as `bg-{{ color }}-600` are not reliably
discoverable by Tailwind's source scanner. Use a static class map when
choosing among known classes, or explicitly include required utilities
with Tailwind v4's `@source inline()` directive. Both approaches make
the required CSS available in the compiled stylesheet.
